# Product

## Loopwise

Loopwise offers in-house formats for product teams (product managers, product owners, UX and
consultants with product duties), from a half-day workshop to multi-week team coaching, including
Agentic Product Management. A sponsor in the customer company inquires through the website, settles
the format in a scoping call, and then prepares it with the academy: participant list, setup check,
expectations survey, follow-up. The academy earns money on booked workshops. This quarter it works
on one path: more inquiries that end in a booking (`product/strategy.md`).

| Persona | Role | Focus |
|---|---|---|
| [Soft sponsor](product/personas/sponsor-soft.md) | supports the AI move, no budget or line authority | names only soft success signals, does not know the format |
| [Hard sponsor](product/personas/sponsor-hard.md) | head of product with budget | wants proof of effect before booking more |
| [Participant](product/personas/participant.md) | PM, PO, BA, UX | same title, very mixed level |

## How to run

```bash
npm start   # http://localhost:3000, PORT overrides
npm test    # node --test
npm run check   # citations point at real lines, quotes match, event names from the list
npm run tree    # draws discovery/kpi-tree.md as discovery/kpi-tree.html
# http://localhost:3000/discovery shows the artefacts as readable pages, the KPI tree drawn
# http://localhost:3000/discovery/map: every opportunity on an evidence map, filterable, read-only
# http://localhost:3000/discovery/tree: the compared candidates linked to the business goal, read-only
```

Node 20 or newer. No dependencies, no `npm install`. Keep it that way.

# Audience and Language

**Audience: developers new to product work**

The trainer changes this one line per cohort, for example to `product managers`.

- **Plain English in every artefact and every reply.** Common words. The writing rules are in
  `.claude/rules/writing.md`, loaded in every session.
- **Loopwise words mean what `product/glossary.md` says.** Use them that way in every artefact.
- **Explain product terms once.** While the audience line names people new to product work, explain
  each product term (opportunity, KPI branch, proxy metric, counter metric, success line, kill
  criterion) in one short sentence the first time it appears in a file. For `product managers`,
  skip these explanations.
- Quotes from sources stay word for word, even when their language is not plain.

# Hard Constraints (Always Apply)

- **English** in every file.
- **Every claim in an artefact quotes its source with location**: file and line, for example
  `sources/interviews/sponsor-soft.md:49`. No quote, no claim. This includes statements about
  rules, limits and strategy ("prices stay off the website"): cite the line in `product/` that says
  it, for example `product/constraints.md:7`, never "by rule" or a section name alone.
- **Only counted numbers.** A number appears only if it is counted from a file in `sources/` or
  `data/`. No scores, no probabilities, no estimated totals, no invented targets.
- **Assessments on three levels, in words:** well supported, partly supported, unsupported. Each
  with reasoning, sources, counter-evidence and gaps.
- **Agents never decide.** Selection fields (chosen opportunity, chosen variant, keep or roll back)
  stay empty for a human. Two exceptions: "Goes into comparison" is written by `compare-opportunities`
  after the human explicitly confirmed or changed its shortlist, with the human's name; and
  `learning-card` writes the decision the pair states, in their words.
- **Synthetic data and composites are labelled** in the file header, and any artefact built on them
  repeats the label.
- Assumptions are written as `[assumption: ...]`.
- No real names, companies, products, places or prices, in material or artefacts.
- If in doubt about evidence, say so and leave the field open. Do not guess.

# Skill chain

Run in this order. Each skill writes its artefact under `discovery/`.

| # | Skill | Writes |
|---|---|---|
| 1 | `kpi-tree` | `discovery/kpi-tree.md`, drawn as `discovery/kpi-tree.html` |
| 2 | `opportunities-from-source` | `discovery/opportunities/<source-group>.md` |
| 3 | `compare-opportunities` | `discovery/opportunity-comparison.md`, drawn at `/discovery/tree` |
| 4 | `intent-and-ideas` | `discovery/intents/<opportunity>.md`: own ideas, more ideas, 3 to 5 with driver and assumption, the idea tested first; drawn at `/discovery/tree` after every step |
| 5 | `test-card <variant> prototype` | `discovery/test-cards/<variant>-prototype.md` |
| 6 | `variant-spec` | `discovery/specs/<variant>.md`, then Claude Code builds `site/variants/<variant>/` |
| 7 | `persona-walkthrough <variant> spec` or `page` | `discovery/user-tests/<variant>-spec.md` or `<variant>-page.md` |
| 8 | `learning-card` | `discovery/decisions/002-<variant>.md` |
| 9 | `test-card <variant> launch` | `discovery/test-cards/<variant>.md` |
| 10 | `read-result` | the `## Result` section of `discovery/test-cards/<variant>.md` |
| 11 | `next-bet` | `discovery/kpi-tree.md` (measured values), `discovery/opportunity-comparison.md` (appended) |

For later, outside the workshop chain: `compare-variants` compares several variants of one
opportunity, each with a launch card, before one ships. It writes `discovery/variant-comparison.md`.

# Decisions

Decisions live in `discovery/decisions/`, one file per decision, each with a named human decider,
the date, the options considered and the artefact it rests on. A skill may prepare a decision; it
never records one on its own. A learning card is a decision record: `learning-card` writes the
pair's own words, and leaves the decision empty if the pair names none.
